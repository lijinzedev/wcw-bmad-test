# Story 4.3: 预警通知联动

## Status
DONE

## Story
As a 安全管理者,
I want 当系统生成监控预警或其他严重事件时能自动通知到责任人（短信/应用推送/站内信）, 
so that 可以第一时间联动处置，缩短响应时间并形成可审计闭环。

## Acceptance Criteria
1. 管理员可在系统中配置“通知规则”（按指标/地点模式/严重级别→通知渠道/对象），支持启停与测试发送。
2. 当产生新的预警记录（如 MonitoringAlert）且命中启用的通知规则时，系统会：
   - 生成一条通知发送记录（含渠道、收件人、主题、内容、事件ID、状态、重试次数、时间戳）。
   - 通过外部通知网关（短信或App推送，占位实现）实际触达；失败会记录原因并按策略重试。
3. 通知发送的所有动作均写入审计日志（含事件ID、规则ID、渠道、收件人数量、结果）。
4. 提供查询接口按时间、渠道、状态分页检索通知记录；前端页面可查看与筛选。

## Dev Notes
### Context & Dependencies
- 本故事依赖 4.2 已产生的 `MonitoringAlert` 预警数据与审计基线；通知集成需遵循 4A 访问控制与统一错误结构 [Source: docs/stories/4.2.安全监控系统对接.story.md; docs/architecture/2-高层架构-high-level-architecture.md#26-安全架构-4a-architecture]

### Design Notes
- 规则匹配优先：metricCode+locationPattern+severity 精确→locationPattern 为空的通配；禁用规则直接跳过。
- 渠道与收件人：初期支持 `SMS`、`PUSH`（字符串枚举），收件人可为用户ID列表或角色（ADMIN/SAFETY_OFFICER）；发送前基于角色解析到用户并去重。
- 失败重试：网络/5xx/网关超时触发重试，解析错误/参数缺失不重试；重试间隔指数退避并限定最大次数。
- 审计与可观测性：所有发送尝试均记录审计事件（事件ID、规则ID、状态、错误摘要）。

### API Specifications
- 新接口统一根路径 `/api/v1`，JWT 鉴权，分页头 `X-Total-Count`/`X-Total-Pages`，错误使用统一结构 [Source: docs/architecture/7-rest-api-规范-rest-api-spec.md#71-通用约定]
- 外部通知网关占位，具体签名/字段待供应商文档确认 [Source: docs/architecture/6-外部-api-external-apis.md#通知网关-api]

### File Locations
- 后端：`int-notification` 客户端与属性放于 `integration/notification` 包；规则/日志实体放 `model`，服务/控制器分别放 `service`/`controller` [Source: docs/architecture/9-项目源代码树结构-source-tree.md]
- 前端：`views/notification/`、`services/notification.js`、`stores/notificationStore.js`，路由 `/admin/notifications` 并在 Admin 导航加入入口。

### Testing Requirements
- 后端：JUnit 5 + MockMvc 覆盖规则匹配、鉴权、分页、重试分支；可使用 `NotificationClient` mock 注入失败/成功分支。
- 前端：Vitest 覆盖规则表单校验、增删改查、测试发送按钮与记录筛选逻辑。

### Technical Constraints
- 严格遵循 4A 权限：仅管理员可管理规则/查看记录；发送动作需最小化敏感信息暴露（如脱敏手机号）。
- 网关不可用时的降级：保证业务事务不回滚，记录失败日志与审计，等待重试。
