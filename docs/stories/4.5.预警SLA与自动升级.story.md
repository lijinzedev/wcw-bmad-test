# Story 4.5: 预警SLA与自动升级

## Status
DONE

## Story
As a 安全负责人,
I want 为不同严重级别/指标配置预警SLA（确认与处置时限）并在超时自动升级与提醒,
so that 提升响应效率、降低漏处置风险，并形成可审计的SLA达标率统计。

## Acceptance Criteria
1. 管理员可配置预警SLA规则（按 `metricCode`/`severity`/`locationPattern`）：确认时限（TTA）、处置时限（TTR）、升级策略（升级渠道/对象/是否转隐患）。
2. 系统定时评估未确认/未处置预警，达到时限自动触发升级与提醒：
   - 未确认超时：发送提醒（含责任对象与超时信息），可选升级到上级责任人或管理群。
   - 未处置超时：可选自动升级为隐患或创建督办记录；同时发送提醒。
3. 所有升级与提醒动作写入审计与通知日志；生成 SLA 违约记录（包含类型、时长、对象）。
4. 提供查询接口与统计：按时间范围输出 SLA 达标率、违约数量、平均确认/处置时长；PC端页面可查看与筛选。

## Dev Notes
### Context
- 4.2 完成预警采集、4.3 完成通知联动、4.4 完成处置与升级为隐患；本故事聚焦“超时策略与自动化闭环”。

### Design
- 规则优先顺序：按 `metricCode+locationPattern+severity` 精确→`locationPattern` 为空的通配；禁用规则跳过。
- 评估策略：
  - 确认时限（TTA）：`alert.createdAt + ackDeadline` 前需 ACK；超时触发 `ACK` 违约与升级提醒。
  - 处置时限（TTR）：若已ACK且未升级为隐患，`acknowledgedAt + resolveDeadline` 前需处置（可定义为“升级为隐患”或“指派+提交整改”）；超时触发 `RESOLVE` 违约。
- 升级动作：通过 `NotificationManagerService` 发送多渠道提醒；当 `autoEscalateToHazard` 为真时自动调用 `MonitoringService.escalateToHazard`。
- 可观测性：所有评估、升级动作写入审计；SLA 违约入库以便统计与追踪。

### API Specifications（拟）
- `GET /api/v1/monitoring/sla-rules`（分页+筛选）/ `POST` / `PUT` / `DELETE`
- `POST /api/v1/monitoring/sla-rules/{id}/test` → 返回在给定 alert 样本下的评估结果（可选）
- `GET /api/v1/analysis/alerts/sla/summary` / `GET /api/v1/analysis/alerts/sla/breaches`

### File Locations

### Testing Requirements
